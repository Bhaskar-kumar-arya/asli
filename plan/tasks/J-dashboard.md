**Gotchas / decisions:**
- `MetricsSummarySchema` (`packages/contracts/src/api.ts`) is intentionally coarse (`accuracy: {sampleSize, precision?, recall?, measuredAt?}`, `cost: {costPer1000ScansUsd?, measuredAt?}`) - the `/dashboard` page needs the accuracy-by-method/condition breakdown and the full per-scan/per-run/10k-projection cost detail the task's own deliverables ask for. Rather than force that detail into the frozen contract, the handler returns the contract's exact fields (schema-validated) plus an `accuracyDetail`/`costDetail` superset the frontend reads directly (documented as such in both `services/metrics/src/handlers/public-metrics.ts` and `apps/web/src/features/dashboard/types.ts`) - same pragmatic move lane S made for its impact-stats gap (see S's Handoff).
- `precision`/`recall` in `MetricsSummary.accuracy` are left `undefined` - `tools/accuracy`'s `AccuracySummary` produces batch-exact/skeleton/manufacturer-STRONG/expiry-exact rates and a tier-correctness rate, never a literal "precision"/"recall" pair, so populating those two fields would mean inventing a mapping that doesn't already exist in the accuracy harness's own vocabulary.
- Cost-per-scan's Lambda-GB-seconds and cost-per-ingestion-run's Step-Functions-transitions/Lambda-GB-seconds are *estimates from documented, named assumptions* (`ASSUMPTIONS` in `services/metrics/src/cost.ts`), not pure CloudWatch measurements - only Bedrock tokens, Textract pages, Translate/Polly characters, ingested-row counts, and scan latency are actually measured off CloudWatch EMF metrics; everything else (API Gateway/S3 request counts per scan, Lambda memory size, Step Functions transition counts) has no per-scan EMF metric emitted anywhere in the codebase, so it's priced via a stated per-scan/per-row multiplier instead. This matches docs/OBSERVABILITY_AND_COST.md's own phrasing ("scans per month assumption, stated explicitly").
